# MVP 완성도를 위한 리뷰 기능 범위 조정 트러블슈팅

## 개요

초기 계획에는 거래 완료 사용자를 대상으로 한 Review CRUD와 리뷰 분석, 사용자 Reputation 계산, AI 매칭 Ranking 연동이 포함되어 있었다. 그러나 남은 개발 기간에 거래 안정화, AI 매칭 완성, 프론트 연동, 성능 개선과 발표 준비를 함께 진행해야 했다. 구현 기능 수를 유지하면 핵심 흐름의 검증이 부족해질 가능성이 높다고 판단해 Review/Reputation을 MVP 범위에서 제외하고 프로젝트 우선순위를 재조정했다.

## S: Situation | 상황

### 초기 역할 분담과 리뷰 계획

AI 기능은 다음과 같이 역할을 나누어 개발할 예정이었다.

- A: 게시글 생성과 Embedding lifecycle
- B: Vector Search, SQL Filtering, Ranking과 추천 이유
- C: Review CRUD, 리뷰 분석과 사용자 Reputation

리뷰는 게시글 평가가 아니라 거래 상대 사용자에 대한 평가로 설계하고, 거래 완료 후 양쪽 사용자가 한 번씩 작성할 수 있도록 계획했다. B의 매칭 결과에는 Reputation 점수를 보조 점수로 반영할 예정이었다.

### 개발 과정에서 늘어난 핵심 작업

구현 과정에서 다음 작업의 중요도와 범위가 예상보다 커졌다.

- 요청글은 1회성이고 재능글은 반복 거래가 가능하다는 규칙을 거래 상태에 반영
- 중복 결제·정산과 지갑 잔액 경합을 방지하기 위한 비관적 락과 DB 제약 적용
- 임베딩 호출을 원본 트랜잭션 커밋 이후로 분리
- 쿠키 인증, CSRF, XSS 방어와 프론트 인증 흐름 정리
- Talent/Request 작성·조회·썸네일·채팅·거래 UI 연동
- Vector Search, SQL 원본 검증, Ranking과 LLM 추천 이유 구현
- 발표 자료와 시연 시나리오 준비

반면 리뷰 기능을 완성하려면 단순 CRUD 외에도 다음 정책과 연동이 필요했다.

- 거래 완료 사용자만 리뷰할 수 있는 작성 권한
- 동일 거래에서 사용자별 한 번만 작성하도록 하는 중복 방지
- 리뷰 수정·삭제가 Reputation 집계에 미치는 영향
- 리뷰 분석 실패와 재처리 정책
- 사용자별 Reputation 계산식과 점수 범위
- B Matching과의 일괄 조회 계약 및 Ranking 가중치
- 프론트 작성·조회 화면과 예외 처리
- 거래, 리뷰, AI 매칭을 연결하는 통합 테스트

남은 기간에 이 범위를 모두 구현하면 기능은 늘어나지만 핵심 거래와 AI 매칭의 안정성, 프론트 완성도와 발표 준비가 함께 낮아질 위험이 있었다.

## T: Task | 과제

다음 기준으로 MVP 범위를 다시 정하는 것이 과제였다.

1. 사용자에게 시연할 핵심 흐름인 게시글 작성, 검색, 채팅과 거래를 완성한다.
2. AI 매칭은 의미 검색, 정확한 SQL 조건 검증, Ranking과 추천 이유까지 동작하게 한다.
3. 구현되지 않은 Reputation 계약과 예약 필드가 코드에 남아 혼란을 만들지 않게 한다.
4. 담당자 간 계약 문서와 실제 코드를 일치시킨다.
5. 리뷰를 제외하더라도 이후 재도입 판단 근거를 남긴다.
6. 범위 축소 후 전체 테스트를 실행해 기존 기능의 회귀가 없음을 확인한다.

## A: Action | 행동

### 1. 리뷰 기능의 실제 완료 조건 분해

Review CRUD만 구현하면 끝나는 작업으로 보지 않고 거래 권한, 중복 방지, 분석, 집계, 매칭 연동, 프론트와 테스트까지 완료 조건을 분해했다. 이를 남은 작업과 비교해 현재 일정 안에서 검증 가능한 품질로 마무리하기 어렵다고 판단했다.

### 2. MVP 우선순위 재설정

사용자 시연에 직접 연결되는 기능을 우선순위로 정했다.

```text
거래 정합성
→ AI 매칭 검색과 추천 품질
→ 프론트 연동
→ 성능 및 보안 점검
→ 발표 준비
```

Review/Reputation은 이 흐름을 완성하는 데 반드시 필요한 기능이 아니며, 충분한 거래와 리뷰 데이터가 없으면 Reputation 효과도 검증하기 어렵다고 판단해 MVP에서 제외했다.

### 3. 미구현 코드와 응답 계약 제거

- 비어 있던 Review 도메인 Controller, DTO, Entity, Repository, Service를 제거했다.
- 비어 있던 AI Reputation Service와 Response를 제거했다.
- 항상 `null`이던 `MatchCandidate.reputationScore`를 제거했다.
- 마이페이지의 동작하지 않는 리뷰 목록 메뉴를 제거했다.
- B Matching이 Review Repository나 미래의 Reputation 계약에 의존하지 않도록 정리했다.

예약 코드를 남겨두면 구현된 기능으로 오해하거나 프론트가 의미 없는 값을 처리하게 되므로, 필요해질 때 명확한 계약과 함께 다시 추가하는 방향을 선택했다.

### 4. AI 매칭 범위 단순화

초기 Ranking은 검증 가능한 두 요소만 사용하도록 유지했다.

```text
semantic similarity
+ 명시적인 금액 조건이 있을 때 amount fit
```

상태, 카테고리, 가격, 예산, 기간과 마감일은 점수가 아니라 SQL 원본 기준 필수 조건으로 검증했다. 서버가 TOP 후보를 확정한 뒤 LLM은 순위를 변경하지 않고 추천 이유만 생성하도록 책임을 제한했다.

### 5. 의사결정과 협업 계약 문서화

- Review/Reputation 제외 결정을 `ADR-003`으로 기록했다.
- AI 개발 가이드에서 C 역할과 Reputation 연동 단계를 제거했다.
- A-B Embedding/Matching 계약만 남기고 B-C 미구현 계약을 제거했다.
- 기존 AI 매칭 ADR에는 `ADR-003`이 이전 계획을 대체한다는 내용을 연결했다.

### 6. 회귀 검증

범위 조정 직후 다음 결과를 확인했다.

- 백엔드 전체 테스트 20개 통과
- Spring ApplicationContext 정상 기동
- 프론트 테스트 7개 통과
- Review/Reputation 코드 참조가 남아 있지 않음을 정적 검색으로 확인

이후 썸네일 응답과 LLM 추천 이유까지 확장한 현재 기준으로는 백엔드 전체 테스트 25개가 통과한다.

## R: Result | 결과 및 배움

### 결과

- 미완성 Review/Reputation 때문에 거래와 AI 매칭 일정이 지연되는 위험을 줄였다.
- 매칭 응답에서 의미 없는 `null` 평판 필드와 미사용 의존성이 제거됐다.
- AI 매칭 책임이 Vector Search, SQL 검증, Ranking과 추천 이유로 명확해졌다.
- 확보한 시간을 거래 동시성 제어, 썸네일 응답, 공개 검색과 LLM 추천 이유 구현에 사용할 수 있었다.
- 코드, 개발 가이드와 ADR이 동일한 MVP 범위를 표현하게 됐다.
- 핵심 사용자 흐름과 발표 시연 범위에 팀의 작업을 집중할 수 있게 됐다.

### 한계

- 거래 상대방에 대한 사용자 피드백을 수집할 수 없다.
- 리뷰가 충분히 쌓인 이후에도 현재 Ranking은 사용자 신뢰도를 반영하지 않는다.
- 추후 재도입 시 Review 권한, 중복 방지와 Reputation 계산 계약을 다시 설계해야 한다.

### 배운 점

- 일정이 제한된 프로젝트에서는 기능 개수보다 핵심 흐름의 완성도와 검증 가능성이 중요하다.
- 기능을 제거할 때는 코드만 삭제하지 않고 응답 DTO, UI, 담당자 계약과 문서를 함께 정리해야 한다.
- 미래 기능을 위한 빈 클래스와 항상 `null`인 예약 필드는 확장성보다 현재 코드의 혼란을 키울 수 있다.
- Reputation은 리뷰 데이터가 충분히 쌓이고 추천 품질 개선을 측정할 수 있을 때 도입해야 의미가 있다.
- 범위 축소도 근거, 영향과 재검토 조건을 남기면 팀의 기술적 의사결정 경험으로 설명할 수 있다.

## 재도입 조건

MVP 발표 이후 다음 조건이 충족되면 Review/Reputation을 별도 기능으로 다시 검토한다.

- 거래 완료 흐름과 리뷰 작성 권한 정책이 확정됨
- 동일 거래의 중복 리뷰를 막는 DB 제약이 설계됨
- 충분한 리뷰 데이터가 축적됨
- Reputation 점수의 범위와 계산식이 합의됨
- Reputation 반영 전후의 추천 품질을 비교할 기준이 마련됨

관련 의사결정은 [ADR-003 리뷰·평판 MVP 제외](../adr/ADR-003-리뷰-평판-MVP-제외.md)에서 확인할 수 있다.
